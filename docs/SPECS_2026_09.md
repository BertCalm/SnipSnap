# Three gaps, specced

Written 2026-09-11, the day the September UAT closed. These are not
defects — the UAT covered those. They are things the app cannot do, or
can only do in one place, found by reading the source after the UAT was
finished.

**Each section ended with a decision that was not mine to make. All
three were answered on 2026-09-11**, and each section now records the
answer under its own heading. The specs are kept as written — the
reasoning that led to each question is worth more than a tidy summary of
what was chosen.

**A caution about this document's own method.** Three of my first four
claims about "missing" features were wrong, and wrong the same way: I
grepped for my own vocabulary, found nothing, and concluded the
capability was absent. This codebase names things in its own language —
the bounce is `Bouncer` and `OrbitEngine.render`, MIDI files are
`MidiGroove`, reversal is five separate `undo` functions. Every "what
exists" line below was checked against the source, and the checks are
named so the next reader can re-run them rather than trust me.

**And that was not enough.** Review of this document's first version
found four more factual errors in it — an overstated MIDI division
range, a voice count I invented, a bin left out, and a printed check
that did not cover its own table. They are corrected below. A document
that claims its claims are checked has to be checked harder than one
that does not, and this one was not, first time.

**Nor was that.** §1 was corrected again on 2026-09-12, and it was the
largest error in the document: it priced the bounce as a missing button
when the button exists, `Bouncer`'s caller is missing because the screen
it serves is unreachable, and GROOVE has no offline render path at all.
The pattern is the same one this preamble opens with, one level up —
the first pass checked what the code *was* and not what *called* it. The
corrected section prints a check for each of its three claims.

## 1. The bounce has an engine and one door

### What exists

| | |
|---|---|
| `loop/OrbitEngine.render` | plays a ring set offline into a `Snip` — "the bounce" |
| `loop/Bouncer.render` | renders a whole **session** offline; `BouncerTest` covers it |
| `audio/WavWriter` | turns a `Snip` into a file |
| `ui/OrbitScreen.kt:558` | the **only** caller of any of it on the phone |

So the phone can bounce an ORBIT ring set, as of today. It cannot bounce
a GROOVE, an arrangement, or a session — and `Bouncer`, which exists for
exactly that, **has no caller anywhere in `:app` or `:cli`**.

Check it: `grep -rn "Bouncer" --include=*.kt */src/main`

### What is missing

> **Corrected 2026-09-12.** This section said what was missing is "a door
> — a button, a destination and a name for the result", at a cost of
> "small-to-medium". That was wrong, and wrong in the way this document
> opens by warning about: written from what `Bouncer` looked like rather
> than from what calls it. What follows replaces it. The three checks are
> printed so the next reader can re-run them rather than trust this twice.

**The door exists, and it already does what was decided.**
`OrbitScreen.kt`'s `bounceToTape()` calls `OrbitEngine.render` and then
`SnipStore.import`: a bounce already lands as a snip. Decision 1 below is
built once, not unbuilt.

Check it: `grep -n "bounceToTape" -A 20 app/src/main/kotlin/com/snipsnap/app/ui/OrbitScreen.kt`

**What cannot bounce cannot bounce for two different, deeper reasons.**

*Sessions.* `Bouncer.render` takes a `Session`, and the only screen that
makes one is `LoopActivity` — which has no launcher intent-filter and is
started by nothing in the app. The manifest says so itself: *"No launcher
filter: one front door. Reachable in dev via `adb shell am start`."* So
`Bouncer` has no caller because the loop grid has no door. Adding a bounce
button there would bounce something a user cannot reach.

Check it: `grep -rn "LoopActivity" --include=*.kt --include=*.xml . | grep -v LoopActivity.kt:`

*GROOVE.* It plays through `PadEngine`, a thin Kotlin owner over a C++
engine — `NativePads.noteOn`, `commitBank`, `stopVoice`. There is no
Kotlin path that renders a groove to a buffer, and writing a second one
would be exactly what `Bouncer`'s own KDoc warns against: *"If bounce and
playback ever disagree, it is a bug in one sink, not two engines that
drifted."*

Check it: `grep -n "NativePads\." app/src/main/kotlin/com/snipsnap/app/PadEngine.kt`

**So the real question is not the one this section asked.** "Where should
a bounce land" is answered and shipped. What is open is *does the loop
grid get a front door* — a product call — and, separately, whether the
native engine learns to render offline, which is DSP work rather than
wiring.

This is also why ORBIT's own refusal reads *"EVERY RING HERE IS A SNIP. A
SNIP IS AUDIO, NOT NOTES — BOUNCE IT INSTEAD"* — it is pointing at a
capability that exists for ORBIT and nowhere else.

### The decision

**Where should a bounce land, and what is it?** Three answers, and they
are genuinely different products:

1. **A snip.** It lands in SNIPS and can be chopped, padded, re-treated.
   The app stays a closed loop — everything it makes, it can eat.
   Cheapest, and the most in character.
2. **An export.** It lands beside the kits on the card, as a WAV to take
   away. Makes the app a thing you finish work in.
3. **Both**, with the second being a share sheet away from the first.

I would build (1) and let EXPORT reach it, because it needs no new
storage concept and because "bounce it, then chop the bounce" is the
loop this app is already best at.

> ### ✅ Decided 2026-09-11: **a snip.**
>
> A bounce lands in SNIPS and is an ordinary snip from that moment —
> choppable, paddable, treatable, bin-able. EXPORT reaches it the same
> way it reaches anything else. The app stays a closed loop.
>
> This also settles ORBIT's *"BOUNCE IT INSTEAD"* refusal: once GROOVE
> and sessions can bounce, the line stops pointing at a door that only
> exists for one screen.

### Cost

**Corrected 2026-09-12**, with the section above. Not small-to-medium —
that estimate priced a button.

- *ORBIT to a snip*: **done.**
- *Sessions*: gated on a product decision (does the loop grid get a front
  door), not on engineering. Once decided, the bounce itself is small —
  one screen action, one `Snip` write, one toast — with the real risk
  being what a long render does to a phone UI, since `Bouncer.render` is
  synchronous and a four-bar session is not a four-bar wait.
- *GROOVE*: **large.** It needs an offline render path that agrees with
  the native engine sample for sample, or it is two engines that drifted.

### How it would be tested

`BouncerTest` already pins the audio. What would be new is the
**refusal** surface: bouncing an empty session, a session whose every
track is muted, a session longer than the app is willing to hold in
memory. That is `:shell` work and mutation-testable, in the shape of
`ExportWizard`'s existing refusals.

## 2. MIDI exists on disk, not on the wire

### What exists

`kit/MidiGroove` reads and writes **Standard MIDI Files** — format 0,
division 960 (the clips' own PPQ, so times survive verbatim), notes on
channel 10 at GM drum numbers. It reads format 0 and 1, **any positive
PPQ division** (`1..0x7FFF`, rescaled to 960), running status, and
refuses both SMPTE-timed files and non-MIDI files with a reason rather
than a crash. `MidiGrooveTest` covers it.

Its own KDoc is right that this is *"the first artifact this codebase
emits that every music tool on earth understands."*

Check it: `sed -n 1,25p kit/src/main/kotlin/com/snipsnap/kit/MidiGroove.kt`

### What is missing

**Live MIDI.** No `android.media.midi`, no `MidiManager`, no device
enumeration, no clock in or out, no transport sync. The app can hand a
file to another tool; it cannot play *alongside* one.

Check it: `grep -rn "android.media.midi\|MidiManager" --include=*.kt .`

### The decision

**Is SnipSnap a sketchpad or an instrument?**

- **Sketchpad** — you make kits here and they go to the MPC. Then live
  MIDI is not a gap at all, and this section should be closed as
  "declined, by design". SMF export already does the job.
- **Instrument** — you play it, possibly alongside gear. Then live MIDI
  is the single biggest functional hole in the app, bigger than the
  bounce, because without a clock it cannot stay in time with anything.

I cannot answer this from the source. The source argues both ways: the
export formats and `Preflight` say sketchpad; PLAY, GROOVE, ORBIT and a
32-voice allocator say instrument (`PadEngine.MAX_VOICES`; the separate
`InstrumentPlayer` runs 8).

> ### ✅ Decided 2026-09-11: **an instrument, synced.**
>
> SnipSnap is played in its own right, alongside other gear. Live MIDI
> is therefore **in scope, including clock and transport sync** — not
> just note input.
>
> **What this commits to, stated plainly.** Sync means the audio
> engine stops owning the timeline. `OrbitClock`, GROOVE's transport
> and the native sink currently assume the app is the master; under
> external clock they follow instead, and every place that converts
> between frames and musical time has to agree on which is authoritative.
> That is an architectural change, not a feature bolted on the side.
>
> **So this does not start as code.** The spec below says half of it is
> worse than none, and that is still true now the question is settled.
> It needs its own design pass — where the timeline lives, what happens
> when clock stops or jumps, what the app does when it is master and
> when it is not — before any of it is written. The decision unblocks
> that design, not an implementation.

### Cost

Large, and larger than it looks. MIDI input is easy; **sync is not**.
Clock means the audio engine's timeline stops being the master, which
touches `OrbitClock`, `GrooveScreen`'s transport and the native sink. I
would not start this without deciding the question above first, because
half of it is worse than none.

### How it would be tested

Message encode/decode is pure and belongs in `:kit` beside `MidiGroove`.
Clock drift and jitter are not unit-testable here and would go on
`docs/BENCH.md` as a live item.

## 3. Undo is five features, not a concept

### What exists

Reversal is real but scattered:

| | |
|---|---|
| `MutateSheet.undo` | one pad's mutation |
| `OutsideSheet.undo` | one pad's outside-source take |
| `Robin.undo` | one pad's round-robin |
| `OrbitScreen`'s undo | the last ring edit |
| GROOVE's `undoTake` | the last recorded take |
| `PadSheet.unTreatState` | a treatment, when the bin still holds the original |
| The takes bin | ejected and displaced pad **audio**, `BIN_KEEP_DAYS` = 30 |
| Shelf bins | deleted kits, snips, rooms — 30 days |

Check it — deliberately wider than the obvious command, because
`grep "fun undo" shell/src/main` finds four of these seven and would have
let this table look complete when it was not:

```
grep -rn "fun undo\|undoTake\|unTreatState\|BIN_KEEP_DAYS =" \
  --include=*.kt shell/src/main app/src/main
```

### What is missing

A single answer to *"that was wrong, go back."* Every reversal above is
a different control in a different place with a different name, and
several exist only while some other condition holds — `unTreatState`
returns `NOT_BINNED` when the original is gone.

The consequence is not that work is lost. It is that **a user cannot
tell, before acting, whether an action is reversible.** That is the same
problem the September UAT's legends solved for hidden gestures, one
level up: reversibility is something you have to learn rather than
something you can see.

### The decision

**Is this worth a real undo stack, or is it a labelling problem?**

- **Labelling** (small): every destructive action names its way back at
  the moment it happens — the toast that says what changed also says how
  to undo it. No new state. Extends a pattern the app already has in
  `Copy`.
- **A stack** (large): a genuine command history with an UNDO in the
  chrome. Every mutating path would have to become an invertible
  operation, which is a rewrite of `KitBuilderModel`'s edit surface.

I would do the labelling first and let it tell you whether the stack is
needed. If the honest label at each site turns out to be "you can't",
that is the argument for the stack — and you will have learned it for
the cost of some copy.

> ### ✅ Decided 2026-09-11: **labelling first.**
>
> Every destructive action names its way back at the moment it happens.
> No new state, no command history.
>
> The stack is not rejected — it is deferred until the labelling has
> said whether it is needed. The test of that is simple and worth
> writing down now: **if writing the honest label at a site requires
> saying "you can't", that site is the argument for a stack.** Count
> those, and the answer decides itself.

### The count, 2026-09-12

The labelling pass is in: `Reversal` holds the app's three answers to
"can I get it back", and `ReversalTest` is a law over every `Copy` String
constant — a line that reads as destructive must say which of the three
applies. The count the decision asked for falls out of that law's own
exclusion list rather than out of anyone's judgement, which is the point.

**Five sites are recorded by the law as having no way back** — that is a
count of *labelled* irreversible sites, not of every irreversible
operation, and the difference matters when reading what follows.

**Three of the five should not have a way back:** emptying the kits,
snips and rooms bins is the one delete this app promises is final, and
all three say so already.

Emptying the *takes* bin is a sixth irreversible operation that the count
does **not** include, because its line does not yet say it is final. It
is parked below until the copy rewrite gives it words; when it gets them
it joins the count and the number becomes six. Either way the two that
follow are still the only two that lose work a user made.

**Two lose work and are the real argument:**

| | what is lost |
|---|---|
| `BAR_WIPED` | the step editor's WIPE BAR — `clearEditorBar` bumps `editorSaveTick`, the autosave writes it, and no control on that screen steps it back. UNDO TAKE is about recorded takes, not editor edits. |
| `FORKED_TO_E_REPLACED` | FORK TO E over an existing PROG E — the old steps are overwritten in place. |

That is **not yet an argument for a command history.** Two sites, both on
one screen, both inside the same feature. The cheaper answer is a
snapshot local to GROOVE's editor, not an invertible operation on every
mutating path in `KitBuilderModel`. Revisit when the count reaches a
third screen; the law will say so, because it fails if the number moves
without this section moving with it.

**One line had been actively lying**, which is the finding that justified
the pass on its own: the bar wipe read *"BAR WIPED. THE MACHINE
FORGIVES."* A user who trusted it lost steps they believed were
recoverable. It now says it cannot be undone and names the recourse that
does exist.

**And the promise had drifted from the sweep.** Four objects each declare
their own bin retention — `KitBuilderModel.BIN_KEEP_DAYS`,
`SnipStore.BIN_DAYS`, `Rooms.BIN_DAYS`, `KitShelf.BIN_DAYS` — while three
`Copy` lines wrote "30 DAYS" as a literal that agreed with all four only
by luck. Changing the retention would have left the app promising the old
number in the user's own language while deleting on the new one. The
sentence is now written once and the four are pinned to it.

**Two gaps are recorded and not fixed**, because their words belong to
the copy rewrite rather than to this pass: `CARD_FORGOTTEN` never says
that picking the card again undoes it, and `BIN_EMPTIED` does not say the
takes bin is emptied for good. Both are open bugs held in
`ReversalTest.awaitingWords`, whose size is asserted so the list cannot
grow quietly.

Check it:

```
./gradlew :shell:test --tests '*ReversalTest*'
```

### Cost

Labelling: small, and mostly `Copy` plus a law that every destructive
toast names its reversal. Stack: large, and it would touch every editing
screen.

## The test seam, which gates all of the above

`:app` has **no test source set**, and CI's JVM job runs
`./gradlew test -x :app:test` — the exclusion is already written for
tests that do not exist.

That module holds the runtime: `PadEngine`, `MixVoice`, `TapeVoice`,
`GrainVoice`, `SurfaceEngine`, `AndroidAudioSink`, `InstrumentPlayer`.
These are the things verified by hand on a phone — choke, voice count,
kit swap during playback, panic — and they have no automated coverage of
any kind.

`PadEngine` is **almost** JVM-testable: 378 lines, and its only imports
are `com.snipsnap.*` and `java.io.File`. The one blocker is
`NativePads`, the JNI bridge, which will not load in a unit test.

**The seam**: an interface in front of `NativePads` so a test can supply
a fake. That would make choke, stealing, panic and kit-swap assertions
ordinary JVM tests.

**Why it is not free**: that interface sits on the audio hot path, and
adding a virtual call and a layer of indirection to the thing that feeds
the sink is exactly the kind of change that trades a real-time glitch
for a testing convenience. It wants measuring, not assuming — which puts
it on `docs/BENCH.md` before it is on anyone's branch.

**What was done instead, today**: the one law that needs no seam —
`ConventionTest`'s *"every voice allocation stops the voices it
displaced"*. Three screens repeat the same line to stop the voices the
allocator choked and stole; a fourth that forgets is a stuck note, and
nothing else in this build would catch it.

**It took three attempts, and the first two are worth recording**,
because they are the same mistake this document opens by admitting:

1. Keyed on the *shape* of the call (`val x = y.noteOn(`). Reported
   `InstrumentPlayer`, which binds `NativePads.noteOn` and steals its own
   voices — right shape, wrong contract. Now keys on the `VoiceAllocator`
   type.
2. Tested `"choked" in src` across the **whole file, comments included**.
   `KitScreen` names both words in a comment above the call, so deleting
   its stop loop would have passed. The mutation check meant to catch
   that happened to pick `PlayScreen`, the one site without such a
   comment. Found in review, not by me.
3. Now strips comments and string literals, finds every `.noteOn(` in a
   file that names `VoiceAllocator` — any call form: `val`, `var`, safe
   call, line break — and requires the cleanup in the lines that follow.
   Mutation-verified against `KitScreen`, the site attempt 2 could not
   protect.

That law is a fence, not a test. It cannot tell you the hat closed. It
can only tell you nobody deleted the line that closes it — and it took
three goes to make it able to tell you even that.
