# Three gaps, specced

Written 2026-09-11, the day the September UAT closed. These are not
defects — the UAT covered those. They are things the app cannot do, or
can only do in one place, found by reading the source after the UAT was
finished.

**Each section ends with a decision that is not mine to make.** Nothing
here is started.

**A caution about this document's own method.** Three of my first four
claims about "missing" features were wrong, and wrong the same way: I
grepped for my own vocabulary, found nothing, and concluded the
capability was absent. This codebase names things in its own language —
the bounce is `Bouncer` and `OrbitEngine.render`, MIDI files are
`MidiGroove`, reversal is four separate `undo` functions. Every "what
exists" line below was checked against the source, and the checks are
named so the next reader can re-run them rather than trust me.

---

## 1. The bounce has an engine and one door

### What exists

| | |
|---|---|
| `loop/OrbitEngine.render` | plays a ring set offline into a `Snip` — "the bounce" |
| `loop/Bouncer.render` | renders a whole **session** offline; `BouncerTest` covers it |
| `audio/WavWriter` | turns a `Snip` into a file |
| `ui/OrbitScreen.kt:558` | the **only** caller of any of it on the phone |

So the phone can bounce an ORBIT ring set, as of today. It cannot bounce
a GROOVE, an arrangement, or a session — and `Bouncer`, which exists for
exactly that, **has no caller anywhere in `:app` or `:cli`**.

Check it: `grep -rn "Bouncer" --include=*.kt */src/main`

### What is missing

A door. The DSP is written and tested; what is absent is a button, a
destination and a name for the result.

This is also why ORBIT's own refusal reads *"EVERY RING HERE IS A SNIP. A
SNIP IS AUDIO, NOT NOTES — BOUNCE IT INSTEAD"* — it is pointing at a
capability that exists for ORBIT and nowhere else.

### The decision

**Where should a bounce land, and what is it?** Three answers, and they
are genuinely different products:

1. **A snip.** It lands in SNIPS and can be chopped, padded, re-treated.
   The app stays a closed loop — everything it makes, it can eat.
   Cheapest, and the most in character.
2. **An export.** It lands beside the kits on the card, as a WAV to take
   away. Makes the app a thing you finish work in.
3. **Both**, with the second being a share sheet away from the first.

I would build (1) and let EXPORT reach it, because it needs no new
storage concept and because "bounce it, then chop the bounce" is the
loop this app is already best at.

### Cost

Small-to-medium. One screen action, one `Snip` write, one toast. The
risk is not in the render — it is in choosing what a long render does to
a phone UI, since `Bouncer.render` is synchronous and a four-bar session
is not a four-bar wait.

### How it would be tested

`BouncerTest` already pins the audio. What would be new is the
**refusal** surface: bouncing an empty session, a session whose every
track is muted, a session longer than the app is willing to hold in
memory. That is `:shell` work and mutation-testable, in the shape of
`ExportWizard`'s existing refusals.

## 2. MIDI exists on disk, not on the wire

### What exists

`kit/MidiGroove` reads and writes **Standard MIDI Files** — format 0,
division 960 (the clips' own PPQ, so times survive verbatim), notes on
channel 10 at GM drum numbers. It reads format 0 and 1, any division,
running status, and refuses a non-MIDI file with a reason rather than a
crash. `MidiGrooveTest` covers it.

Its own KDoc is right that this is *"the first artifact this codebase
emits that every music tool on earth understands."*

Check it: `sed -n 1,25p kit/src/main/kotlin/com/snipsnap/kit/MidiGroove.kt`

### What is missing

**Live MIDI.** No `android.media.midi`, no `MidiManager`, no device
enumeration, no clock in or out, no transport sync. The app can hand a
file to another tool; it cannot play *alongside* one.

Check it: `grep -rn "android.media.midi\|MidiManager" --include=*.kt .`

### The decision

**Is SnipSnap a sketchpad or an instrument?**

- **Sketchpad** — you make kits here and they go to the MPC. Then live
  MIDI is not a gap at all, and this section should be closed as
  "declined, by design". SMF export already does the job.
- **Instrument** — you play it, possibly alongside gear. Then live MIDI
  is the single biggest functional hole in the app, bigger than the
  bounce, because without a clock it cannot stay in time with anything.

I cannot answer this from the source. The source argues both ways: the
export formats and `Preflight` say sketchpad; PLAY, GROOVE, ORBIT and a
16-voice allocator say instrument.

### Cost

Large, and larger than it looks. MIDI input is easy; **sync is not**.
Clock means the audio engine's timeline stops being the master, which
touches `OrbitClock`, `GrooveScreen`'s transport and the native sink. I
would not start this without deciding the question above first, because
half of it is worse than none.

### How it would be tested

Message encode/decode is pure and belongs in `:kit` beside `MidiGroove`.
Clock drift and jitter are not unit-testable here and would go on
`docs/BENCH.md` as a live item.

## 3. Undo is four features, not a concept

### What exists

Reversal is real but scattered:

| | |
|---|---|
| `MutateSheet.undo` | one pad's mutation |
| `OutsideSheet.undo` | one pad's outside-source take |
| `Robin.undo` | one pad's round-robin |
| GROOVE's UNDO TAKE | the last recorded take |
| `PadSheet.unTreatState` | a treatment, when the bin still holds the original |
| Bins | deleted kits, snips, rooms — 30 days |

Check it: `grep -rn "fun undo" --include=*.kt shell/src/main`

### What is missing

A single answer to *"that was wrong, go back."* Every reversal above is
a different control in a different place with a different name, and
several exist only while some other condition holds — `unTreatState`
returns `NOT_BINNED` when the original is gone.

The consequence is not that work is lost. It is that **a user cannot
tell, before acting, whether an action is reversible.** That is the same
problem the September UAT's legends solved for hidden gestures, one
level up: reversibility is something you have to learn rather than
something you can see.

### The decision

**Is this worth a real undo stack, or is it a labelling problem?**

- **Labelling** (small): every destructive action names its way back at
  the moment it happens — the toast that says what changed also says how
  to undo it. No new state. Extends a pattern the app already has in
  `Copy`.
- **A stack** (large): a genuine command history with an UNDO in the
  chrome. Every mutating path would have to become an invertible
  operation, which is a rewrite of `KitBuilderModel`'s edit surface.

I would do the labelling first and let it tell you whether the stack is
needed. If the honest label at each site turns out to be "you can't",
that is the argument for the stack — and you will have learned it for
the cost of some copy.

### Cost

Labelling: small, and mostly `Copy` plus a law that every destructive
toast names its reversal. Stack: large, and it would touch every editing
screen.

## The test seam, which gates all of the above

`:app` has **no test source set**, and CI's JVM job runs
`./gradlew test -x :app:test` — the exclusion is already written for
tests that do not exist.

That module holds the runtime: `PadEngine`, `MixVoice`, `TapeVoice`,
`GrainVoice`, `SurfaceEngine`, `AndroidAudioSink`, `InstrumentPlayer`.
These are the things verified by hand on a phone — choke, voice count,
kit swap during playback, panic — and they have no automated coverage of
any kind.

`PadEngine` is **almost** JVM-testable: 378 lines, and its only imports
are `com.snipsnap.*` and `java.io.File`. The one blocker is
`NativePads`, the JNI bridge, which will not load in a unit test.

**The seam**: an interface in front of `NativePads` so a test can supply
a fake. That would make choke, stealing, panic and kit-swap assertions
ordinary JVM tests.

**Why it is not free**: that interface sits on the audio hot path, and
adding a virtual call and a layer of indirection to the thing that feeds
the sink is exactly the kind of change that trades a real-time glitch
for a testing convenience. It wants measuring, not assuming — which puts
it on `docs/BENCH.md` before it is on anyone's branch.

**What was done instead, today**: the one law that needs no seam —
`ConventionTest`'s *"every voice allocation stops the voices it
displaced"*. Three screens repeat the same line to stop the voices the
allocator choked and stole; a fourth that forgets is a stuck note, and
nothing else in this build would catch it. It found a false positive on
its first run (`InstrumentPlayer` binds `NativePads.noteOn` and steals
its own voices) which is why it keys on the `VoiceAllocator` type rather
than the shape of the call.

That law is a fence, not a test. It cannot tell you the hat closed. It
can only tell you nobody deleted the line that closes it.
