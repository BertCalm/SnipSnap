# SILK Phase 2 Implementation Plan — SANTUR

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship SILK's third voice, SANTUR — a four-loop course driven by a
mallet (not a pick), a *fixed* (sourced, not knobbed) stiffness dispersion,
and a sympathetic resonator bank (WASH) tuned to the current SCALE's degrees
across three octaves — registered end to end the way OUD and GUZHENG are.

**Architecture:** Phase 1b's rule continues: every new `Strings` stage
defaults to off and reduces to Phase 1a's proven loop; nothing here is
allowed to move PLUCK's two proofs or Phase 1b's own SilkTest/StringsTest
claims. SANTUR needs two genuinely new pieces of DSP — `Exciter.mallet` (a
raised-cosine force pulse) and the WASH bank (a *dynamic* `Modes.Mode` list
built from `SilkScales`, not a fixed body table) — plus one fix to existing
code: `Strings.course`'s own per-loop feedback step, which Phase 1b's own
OUD work found measurably detunes a same-frequency unison sum, and which
Phase 1b left as this phase's problem to inherit (that PR's own commit
message names it explicitly).

**Tech Stack:** Kotlin/JVM (`:synth` module, Gradle, JDK 17, JUnit via
`kotlin("test")`), reusing `Strings`, `Modes`, `SilkScales`, and the same
registration points Phase 1b already wired generically (`SilkPatch`,
`Velocity.kt`).

**Spec:** `docs/superpowers/specs/2026-09-27-silk-string-engine-design.md` —
"Architecture" (the exciter/course/body/[sympathetic bank] diagram), "How
much B" (SANTUR's sourced B), "SANTUR — four strings and the wash", "Macros",
"Testing" (items 1 and the SANTUR partial-stretch row), "Phasing and gates"
(row 2).

**Research:** `docs/superpowers/plans/2026-09-27-silk-research.md` §4
(santur) — every sourced number below cites back to it.

## Why this phase's shape

SANTUR is phased after OUD/GUZHENG and before SHAMISEN because its two new
stages are both **linear**: a force-pulse exciter and a bank of independent
linear resonators. No nonlinearity, no stability risk beyond the allpass
coefficient bound Phase 1b's `Dispersion.forB` already enforces (and now
clamps, per that PR's own review round). SHAMISEN's sawari — the loop's one
nonlinear stage — stays last, on a toolkit this phase will have exercised
further.

- **PLUCK's two proofs, and Phase 1b's own SilkTest/StringsTest claims, stay

### Task 1: Fix `Strings.course`'s own tuning/feedback interaction

Phase 1b's OUD work needed "slightly unequal feedback" between its two
course loops and found, empirically, that reusing `Strings.course`'s own
existing 1%-per-loop `fbK` step (`damping.fb * (1f - 0.01f * k)`) measurably
detunes the *summed* output at COURSE 0 (true unison, where the loops'
only remaining difference is that feedback split) — several cents off the
5-cent bound OUD's own tuning test carries. OUD worked around it locally
with a much smaller step (0.2%) and a test that only covers its own N=2
case. `Strings.course` itself has never been called with `count > 1` in
production and has no tuning-accuracy test at `count > 1` to have caught
this — SANTUR is the first real caller, at N=4, where four loops' combined
feedback spread would make the same interaction worse, not better.

- [ ] **Step 1: Reproduce the interaction directly in `StringsTest`, with
  excitation controlled out.** `Strings.course` seeds each loop's own
  `pluck` differently even at `spread = 0` (`Dsp.seedFor(seed, "COURSE",
  k)`), so feedback is not the only thing varying between loops — a single
  FFT of the summed, differently-excited output can pass or fail on
  exciter-noise luck rather than on the fb step itself. Isolate the fb
  step specifically: either add a test-only `course` overload (or a small
  test helper that calls `Loop` directly, the way `StringsTest`'s own
  `the loop passes its input straight through` test already constructs a
  bare `Loop`) that drives every loop with the *identical* exciter burst,
  varying only `fbK`, or run the real `Strings.course(count = 4, spread =
  0f, ...)` across several different seeds and require the tuning bound to
  hold on *every* one (ruling out excitation luck by exhausting it rather
  than removing it). Keep a separate, real `Strings.course` end-to-end
  regression alongside whichever isolation approach is chosen — the
  isolation test proves the mechanism, the end-to-end one proves the
  actual caller path. Confirm the failure first on the controlled version
  — this is the "revert and watch it fail for the right reason"
  discipline, applied to a fix instead of a claim: prove the bug
  reproduces, from the fb step alone, before changing anything.
- [ ] **Step 2: Fix `Strings.course`'s own `fbK` step.** Reduce it to
  whatever step size Step 1's own measurement shows keeps every loop count
  1–4 within 5 cents at spread 0 (Phase 1b's OUD fix used 0.2% per loop for
  N=2; N=4's worst-case spread across four unequal-feedback loops may need
  a smaller step still — measure, don't assume the same constant transfers).
  Keep the "pair decays unevenly" character the spec asks for (spec,
  "Architecture" table: `Course` "each with a slightly different feedback
  so the pair decays unevenly") — the fix is the step's *size*, not
  removing the mechanism.
- [ ] **Step 3: Backport the smaller step to `Silk.kt`'s own OUD fbK.**
  Once `Strings.course`'s own constant is correct, decide whether OUD
  should call `Strings.course` directly instead of its own
  `oudCourseLoop` (it currently can't, because OUD's SLIDE needs the
  per-sample pitch envelope `Strings.course` doesn't expose) or simply
  match the corrected constant. Don't leave two different magic numbers
  for the same physical effect without a comment explaining why they
  differ, if they still do.
- [ ] **Step 4: Verify.** `StringsTest` (including the new N=4 tuning
  test) and `SilkTest`'s own `OUD is in tune at every degree of RAST` both
  green. Commit.

### Task 2: `Exciter.mallet`

- [ ] **Step 1: Design the pulse.** A raised-cosine force pulse (spec,
  "Architecture": `Exciter.mallet`, "a raised-cosine force pulse; width is
  hardness"; "SANTUR": "PICK is mallet hardness (pulse width: wide and dark
  to narrow and bright)"). Contact time is shape (spec: "no mezrab is
  measured; the piano proxy runs from about 4 ms in the bass to under 1 ms
  in the treble" — cite as the informing proxy, not a source for SANTUR
  itself, the same "shape, informed by a proxy" language Phase 1b used for
  OUD's course spread). One pulse, no bounce — the spec's own explicit
  choice ("the sources disagree on whether a mezrab rebounds, and one pulse
  is the simpler default").
- [ ] **Step 2: Implement in `Strings.kt`.** `fun mallet(n: Int, freq: Float,
  hardness: Float, position: Float, seed: Int, rate: Int, maxLen: Int):
  FloatArray` (mirror `pluckExciter`'s own signature shape where it
  applies — `position` reuses STRIKE's existing comb, since STRIKE's
  meaning doesn't change for SANTUR). Zero-mean it the same way
  `pluckExciter`'s burst is (same reasoning: a DC offset survives as a
  fake sub-thump).
- [ ] **Step 2b: Make the exciter pluggable on `Strings.course` (and
  `Strings.pluck`, which it's built on).** As written today, `course` always
  calls `pluck`, and `pluck` always calls `pluckExciter` internally — there
  is no seam for a caller to supply `mallet` instead, so SANTUR's own
  `course(count = 4, ...)` call in Task 5 would still be pick-driven.
  Add an `exciter` parameter — a function type shaped like `pluckExciter`'s
  own signature, e.g. `(n: Int, freq: Float, pickHz: Float, position: Float,
  seed: Int, rate: Int, maxLen: Int) -> FloatArray` — to both `pluck` and
  `course`, defaulting to `::pluckExciter` so every existing call site
  (PLUCK, SITAR, OUD, GUZHENG) compiles and renders unchanged with no edit.
  `mallet`'s own `hardness` parameter maps onto that shared signature's
  `pickHz` slot the same way PICK already means "exciter brightness" on
  every voice (spec, "Macros": "PICK | exciter brightness; mallet hardness
  on SANTUR") — one shared shape, not a second parallel parameter.
- [ ] **Step 3: Test.** A `StringsTest` case per the spec's own shape
  claims: PICK narrow (hardness high) is brighter (higher spectral
  centroid) than PICK wide, at the *onset* specifically (a mallet's own
  transient, not the string's later ring — measure the first few ms).
  Determinism (same seed, same bytes). Zero-mean (same assertion style as
  the existing pick-burst test).
- [ ] **Step 4: Verify and commit.** `StringsTest` green; PLUCK/OUD/GUZHENG
  untouched (this is new code, not a modification of `pluckExciter`).

### Task 3: SANTUR's fixed dispersion — wire it, then measure it honestly

SANTUR's own sourced `B = 3.1 × 10⁻⁴` (Heydarian, spec "How much B") is
roughly double GUZHENG's own STIFF ceiling (`STIFF_B_MAX = 1.5e-4`), and
Phase 1b's GUZHENG work found that `Strings.Dispersion.forB` at GUZHENG's
own B range produces a partial stretch three orders of magnitude under what
the underlying physics (`fk = k·f0·√(1+B·k²)`) predicts — correct in sign
and mechanism, proven at the `Strings` level with a deliberately strong
synthetic coefficient, but not yet audible or measurable at real B. Because
SANTUR's own B is fixed rather than user-facing, this phase gets to find out
directly whether the same weakness holds at 2× GUZHENG's ceiling, rather
than inferring it.

- [ ] **Step 1: Wire `Strings.Dispersion.forB(3.1e-4, STIFF_SECTIONS)`
  into SANTUR's loop construction**, unconditionally (not a knob — the
  spec is explicit: "not on a knob (see the voice)").
- [ ] **Step 2: Measure the partial stretch at this B, against a concrete
  criterion — not the spec's own vague "fit tolerance" line.** The
  `StringsTest` stiffness-sharpening test this phase's spec citation
  points to doesn't define a numeric B-fit tolerance at all: it drives a
  synthetic `a = -0.9` probe (not a B value) and only checks monotonicity
  plus `last > 1.001`, so "within the fit tolerance the STIFF test uses"
  names a tolerance that doesn't exist anywhere in the codebase. Replace
  it with a criterion this phase actually defines: compute each partial
  `k`'s *predicted* stretch from the closed-form physics the spec itself
  cites (`fk = k·f0·√(1+B·k²)`, at `B = 3.1e-4`, for `k` 1–8), compute the
  *measured* stretch from the rendered SANTUR loop the same way the
  existing GUZHENG probe does (measured frequency of partial `k` divided
  by `k·f0`), and require them to agree within some explicit, stated
  tolerance (a percentage of the predicted stretch, or a fixed cents
  bound — pick one and write it down here or in the test's own comment,
  not "close enough").
- [ ] **Step 3: Report the measurement plainly, whichever way it comes
  out.** If measured and predicted agree within Step 2's own stated
  tolerance, ship that test. If it reproduces GUZHENG's own under-strength
  finding (likely, given B is the same order of magnitude and the
  mechanism is identical), do **not** raise `STIFF_SECTIONS` or otherwise
  tune the coefficient to force a passing number without a sourced
  justification — that would be papering over the same gap Phase 1b
  explicitly declined to paper over. Instead: write the honest finding
  into the code (comment, mirroring `Silk.guzheng`'s own) and into this
  phase's roadmap row, and open it as a named follow-on (closing it needs
  the per-note re-derivation the papers' own piano application does, same
  as GUZHENG's own open question — these two may turn out to be the same
  follow-on task). Whichever outcome, keep the *sign/monotonicity* test
  from Step 1's wiring regardless — that one's mechanism-level, not
  magnitude-level, and Phase 1b's own STIFF test already proves the same
  pattern holds at this scale.
- [ ] **Step 4: Verify and commit**, whichever outcome Step 3 lands on.

### Task 4: The WASH sympathetic bank

Unlike OUD's and GUZHENG's fixed `bodyFor` tables (one measured instrument,
gains and t60s baked in), WASH's bank is **dynamic** — tuned to whichever
SCALE the pad is currently set to, across three octaves (spec, "SANTUR":
"a bank of resonators... tuned to the current SCALE's degrees across three
octaves... The bank follows SCALE, so a SHUR santur rings in SHUR").

- [ ] **Step 1: Build the mode list from `SilkScales`, without duplicating
  modes at the octave seams.** A private `washModesFor(root: Float, scale:
  SilkScales.Scale, ...): List<Modes.Mode>` in `Silk.kt` (not `Strings.kt`
  — this is SILK-specific business logic over `SilkScales`, not a generic
  string primitive; `Strings.bodyRing` already accepts any
  `List<Modes.Mode>` and needs no change). `scale.cents` already starts at
  0; naively adding "the top-of-period degree" *and* looping three whole
  octave copies double-books every seam (octave 0's top-of-period degree
  and octave 1's degree-0 land on the identical frequency, and the same
  collision repeats between octaves 1 and 2) — each such frequency would
  get two resonators stacked on it instead of one, quietly doubling WASH's
  gain at exactly the scale's own root-adjacent degrees and nowhere else.
  Generate the *inclusive* three-octave span with each frequency appearing
  once: walk `scale.cents` (its own degrees, no separate top-of-period
  entry) across octaves 0, 1, and 2 for the within-octave degrees, then
  add exactly one further mode at the span's own top (`root` transposed by
  3 literal octaves — 3600 cents — using `scale.period` doesn't apply here
  either, only literal octaves do, so this is one closed-form top note,
  not a fourth octave of the whole table). `hz = root * 2^((cents +
  1200*octave) / 1200)`. On BOHLEN_PIERCE specifically (period ≈ 1901.955
  cents, not 1200): "the current SCALE's degrees across three octaves"
  still reads literally as three 1200-cent spans in this design, so a
  BOHLEN_PIERCE SANTUR's degrees simply don't land on that scale's own
  period boundary — state this explicitly in the code comment rather than
  leaving a silent surprise for whoever pairs SANTUR with BOHLEN_PIERCE
  first. Use `Modes.fixed(hz, gain, t60)` per mode, matching how
  `Strings.bodyRing`'s own fixed-table callers already build absolute-Hz
  modes (`Modes.ring`'s `fundamentalHz` argument is `1f` for that reason —
  `bodyRing` always calls it that way, so `Modes.fixed`'s `ratio = hz`
  parameter *is* the absolute Hz here, not a multiplier).
- [ ] **Step 2: WASH drives level and t60 together**, per the spec
  ("WASH sets the bank's level and its t60 together"). One macro, two
  effects: `t60 = Dsp.lin(wash, t60Floor, t60Ceiling)` (both ends shape,
  labelled as such — "a few seconds" is the only source) feeding into each
  mode's own `t60`, and `wash` itself as `Strings.bodyRing`'s `amount`
  argument for level. Chosen so WASH 0 is silent (no bank at all) and WASH
  1 is "past the real instrument" (spec, "Macros": "Every character macro
  at 0 is the plain string, and at 1 is past the real instrument").
- [ ] **Step 3: Wire it into `synthesize`'s SANTUR branch**, chained after
  `withBody` (architecture diagram: `body (Modes) -> [sympathetic bank]`),
  driven by the *un-inflected* pitch per the spec's own INFLECT note
  ("WASH's sympathetic bank stays on the un-inflected... " — read the
  spec's INFLECT section in full before this step; Phase 1b's own INFLECT
  work may already have context worth reusing on exactly this point).
- [ ] **Step 4: Test the two claims from the spec's "Testing" section.**
  "The tail after the string's own t60 is louder with WASH 1 than 0" (an
  RMS-in-the-tail-window comparison, not a peak comparison — the string
  itself has already decayed past its own t60 by construction) — "its
  spectral peaks sit on the SCALE's degrees" (an FFT peak-picking test
  reusing this phase's own Task 1 helper, checking that the tail's
  loudest peaks land near the scale's own degree frequencies, not at
  arbitrary points).
- [ ] **Step 5: Verify and commit.**

- [ ] **Step 1: Add `SANTUR` to `enum class SilkVoice`.** This forces every

  for a third voice, only compile-forced branches inside `Silk.kt` itself.
- [ ] **Step 2: `rootFor(SANTUR) = 164.81f` (E3)** — spec: "Root E3", "the
  9-bridge santur runs E3–F6, about 165–1397 Hz". **This root alone does
  not reach F6.** `SilkScales.frequencyFor`'s TUNE spans exactly two
  periods above the root for every voice (shared infrastructure since
  Phase 1b, unchanged here) — for SHUR (SANTUR's own default, a 7-degree,
  1200-cent-period scale) that's E3 to E5, not E3–F6's roughly 3-octave
  span. This is not a SANTUR-specific gap to close in this phase: every
  SILK voice's TUNE already covers a sub-range of its real instrument's
  full range this same way (OUD's real neck length exceeds two periods of
  RAST too), and widening the shared two-period convention is bigger than
  one voice's own task list. Resolve it explicitly rather than silently:
  keep the two-period convention, and correct any plan or doc language
  that reads E3–F6 as a completeness claim TUNE must satisfy — it
  describes the real instrument's total range, not this pad voice's own
  reachable span. If the eventual listening gate finds two periods of
  SHUR too narrow for SANTUR specifically, that becomes its own follow-on
  question (a wider default TUNE span for this voice only), not something
  to solve by construction here.
- [ ] **Step 3: `macrosFor(SANTUR)`** — the same nine-macro shape as OUD
  and GUZHENG (spec, "Macros" table): TUNE/SCALE (default SHUR, per spec
  "Each voice defaults to its own tradition's scale... SANTUR → SHUR")
  /INFLECT/DAMP/PICK (mallet hardness)/STRIKE/BODY/COURSE (spread of the
  four, "defaults **near 0**" — every source says the four are tuned to
  exact unison, spec is explicit that no spread is measured)/WASH.
- [ ] **Step 4: `synthesize`'s SANTUR branch** — `Strings.course(freq,
  ..., count = 4, spread = course, exciter = ::mallet, ..., dispersion =
  Strings.Dispersion.forB(SANTUR_B, STIFF_SECTIONS))`, using Task 2 Step
  2b's own `exciter` parameter to actually reach the mallet rather than
  the pick burst `course`/`pluck` default to, then `withBody` (SANTUR's
  own neutral-shape body table, spec:
  "no santur body mode is measured; BODY is a neutral shape and says so"
  — a single wide, low-Q, explicitly-labelled placeholder mode, not an
  empty table, so BODY still does something at BODY > 0), then Task 4's
  `washModesFor`-driven bank.
- [ ] **Step 5: Verify against this voice's own tuning claim** (item 1,
  generalised): every degree of SHUR (SANTUR's default) within 5 cents,

## What Phase 3 (SHAMISEN) inherits

- `Strings.Course` is now proven at every count 1–4, tuning-accurate.
- `Exciter.mallet` and `Exciter.pluck` both exist; SHAMISEN's own slap is
  a third, separate exciter/envelope layered on top of a pick-style burst
  (spec: "strike splits into string + skin... the slap needs its own short
  envelope"), not a reuse of either.
- `Strings.Collision` (sawari/jawari's one-sided fold-back obstacle) is
  SHAMISEN's own new DSP — nothing in Phase 2 anticipates it. It is also
  PLUCK's own SITAR jawari, already proven in `Strings.kt` since Phase 1a
  (PLUCK Phase 3a) — SHAMISEN's Collision work is wiring a proven
  mechanism to a second voice, not inventing one.
- The WASH bank's "build a dynamic `Modes` list from `SilkScales`" pattern
  is reusable if a future voice needs scale-following resonance; SHAMISEN's
  own spec does not currently ask for one.
