# SILK Phase 3 Implementation Plan — SHAMISEN

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship SILK's fourth voice, SHAMISEN — a single bright, short-ringing
string carrying a built-in pitch glide, a sawari buzz (the loop's one
nonlinearity), and a bachi/skin strike layered in parallel — registered end
to end the way OUD, GUZHENG and SANTUR are.

**Architecture:** Phase 1b's rule continues: every new stage defaults to off
or reduces to what already exists; nothing here is allowed to move PLUCK's
two proofs or Phase 1b/2's own SilkTest/StringsTest claims. Unlike SANTUR,
SHAMISEN needs **no new `Strings.kt` primitive at all** for its own
nonlinearity: the spec's own `Collision` (a one-sided obstacle: displacement
past a threshold is folded back with a loss) is already shipped, as
`Strings.Loop`'s `jawari`/`jawariP0` parameters, threaded through
`Strings.pluck` since PLUCK Phase 3a (SITAR). SAWARI is that mechanism
reused on a second voice, not a new one — the spec says this outright
("Strength needs no second knob — it follows the string's amplitude, as the
jawari outline in PLUCK's spec already reasons"), and the Phase 2 plan's own
closing section named this inheritance before this phase began. What *is*
new: SHAMISEN's own built-in pitch-glide envelope (a `Loop.retune` caller,
same mechanism as OUD's SLIDE and GUZHENG's PRESS but automatic rather than
knobbed), a fixed body table (frame + neck modes), and SLAP — a short noise
burst through a small skin `Modes` table, mixed in parallel with the string
rather than driven by it, which needs a small new Silk.kt-private helper
(`bodyRing`'s own drive-equals-dry-carrier shape doesn't fit a synthetic
burst).

**Tech Stack:** Kotlin/JVM (`:synth` module, Gradle, JDK 17, JUnit via
`kotlin("test")`), reusing `Strings.pluck`'s existing `jawari`/`dispersion`
parameters, `Modes`, `SilkScales`, and the same registration points Phase
1b/2 already wired generically (`SilkPatch`, `Velocity.kt`).

**Spec:** `docs/superpowers/specs/2026-09-27-silk-string-engine-design.md` —
"Architecture" (the `Loop`/`Collision` table), "SHAMISEN — sawari and the
slap", "Macros", "Testing" (items 1, and the SAWARI/SLAP bullets under "The
rest"), "Phasing and gates" (row 3).

**Research:** `docs/superpowers/plans/2026-09-27-silk-research.md` §1
(shamisen) — every sourced number below cites back to it by row ID (P/G/B/R/A/D/S/T-prefixed).

## Why this phase's shape

SHAMISEN lands last because its sawari is the loop's one nonlinearity — the
one piece with a stability risk — and the spec's own reasoning was to ship
it "on a toolkit that has already been listened to." Practically, that risk
turns out to already be retired: `jawari`'s fold-back is proven stable
(SITAR has shipped on it since PLUCK Phase 3a) and provably lossy by
construction (`yy -= jawari * min(yy, jawariP0) * yy / jawariP0`, a
subtraction of a bounded positive quantity, never an addition — the design's
own risk-table entry, "the fold-back loss is `< 1` by construction", is
already true of shipped code, not something this phase has to build). What
this phase actually adds that's new is small and linear: a body table, a
pitch envelope, and a parallel noise-driven resonator layer.

## Global Constraints

- **PLUCK's two proofs, and Phase 1b/2's own SilkTest/StringsTest claims,
  stay green throughout.** Run `PluckTest`, `StringsTest`, and `SilkTest`
  before Task 1's first edit and after every later task.
- **Every new stage defaults to off / reduces to what already exists.**
  SAWARI at 0 is `jawari = 0f` — `Strings.pluck` already skips the fold-back
  entirely at that value, so this is a macro wiring, not a new code path
  to gate. SLAP at 0 must return the string untouched, the same "amount 0 is
  the input, byte for byte" contract `Strings.bodyRing` already carries.
- **Don't guess at unsourced physics; say what's shape.** The skin's own
  fundamental mode is *unresolved* between two conflicting measurements from
  the same lab (B5 ≈ 151.7 Hz vs B6 ≈ 766.4 Hz — research §1, N.3 verifier
  note i) — ship one placeholder mode, explicitly labelled, the same
  discipline SANTUR's own neutral body table followed. SHAMISEN's own
  dispersion coefficient has no source at all (no B is measured for silk or
  nylon shamisen strings anywhere in the research) — its only job is to keep
  the sawari buzz's precursor from vanishing (T8: "with EI = 0 the precursor
  disappears"), not to claim a stretch, and the code must say so.
- **A sourced number that conflicts with the design's own test bound gets
  flagged, not silently dropped or silently kept.** G1's pitch glide settles
  toward "0.8 %" rather than 0 % — about 14 cents, past the 5-cent bound
  every other SILK tuning test enforces. Task 2 resolves this explicitly
  (see its own note) rather than letting the implementation quietly ignore
  one side of the tension.
- **Never commit or push on an unverified test run.** Every commit is
  preceded by a genuine `BUILD SUCCESSFUL` (fresh XML timestamps, exit code
  checked, never grepped output) — the standing rule from every prior phase.

### Task 1: SAWARI — reuse `Collision`, wire a fixed small dispersion

- [ ] **Step 1: Confirm the reuse compiles as expected, no `Strings.kt`
  edit.** `Strings.pluck(freq, seconds, damping, pickHz, seed, rate,
  position, stiffness = 0f, jawari = sawariMacro, dispersion =
  shamisenDispersion, exciter = ::pluckExciter)` — SAWARI's own knob value
  passed straight through as `jawari`, 0..1 (spec: "SAWARI is the obstacle's
  depth: 0 = no contact, 1 = the string grazing the neck on every swing").
  `pluck` already computes `jawariP0` internally via `burstPeak` whenever
  `jawari > 0f`, so the reference peak SAWARI's amplitude-following depends
  on ("the buzz must never add energy") needs no new plumbing either.
- [ ] **Step 2: Pick SHAMISEN's own fixed dispersion coefficient and wire it
  unconditionally** (not a knob — there is no STIFF macro for this voice;
  see Task 3's macro list). No B is measured for shamisen strings anywhere
  in the research; the guqin/guzheng proxies (B ≈ 9e-5, B ≈ 3.5e-5) are
  wound or nylon-over-steel strings, structurally stiffer than SHAMISEN's
  own plain silk or nylon (research §1, F7, ST1/ST1c) — pick something
  smaller than GUZHENG's own anchor (`STIFF_B_ANCHOR = 3.5e-5`) as a starting
  point, and say in the constant's own KDoc that its only sourced
  justification is T8 (the precursor needs *some* nonzero stiffness to
  exist at all), not a stretch-magnitude claim. Reuse
  `Strings.Dispersion.forB(b, STIFF_SECTIONS)`, the same helper GUZHENG and
  SANTUR already call.
- [ ] **Step 3: Test the spec's own SAWARI signature** (spec, "Testing",
  "The rest": "with SAWARI above 0 the energy in partials 6–20 is higher and
  longer-lived than at 0, and the spectral centroid is higher — the biwa
  measurement's signature"). This is the closest sourced analogue SILK has
  to a shamisen-specific sawari measurement (S8/S8b, biwa, a different but
  related instrument's sawari) — reuse `StringsTest`'s existing
  `spectralCentroid` helper (built for the mallet-brightness test) rather
  than writing a second one. Do **not** assert monotonicity across the full
  SAWARI range — the spec is explicit that the real effect has a sweet spot
  and "too-deep can die faster" (research §1, F10) — assert only the
  direction at a moderate SAWARI value against SAWARI 0, and separately
  assert the design's own hard guarantee: render at SAWARI 1 / PICK 1 (the
  spec's own worst case) and confirm the envelope never rises after the
  attack (spec, "Failure handling": "Collision adds energy | ... a test
  renders SAWARI 1 at PICK 1 and asserts the envelope never rises after the
  attack").
- [ ] **Step 4: Verify and commit.** `StringsTest`/`SilkTest` green; no
  `Strings.kt` production code changed in this task (only, if anything, new
  test-only helpers).

### Task 2: The built-in pitch glide

Unlike OUD's SLIDE and GUZHENG's PRESS, this is not a macro — it fires on
every note, scaled by PICK (spec: "a harder stroke stretches the string
further"), and it moves the *opposite* direction from every existing
`Loop.retune` caller: those all glide from a lower frequency up to a higher
one; SHAMISEN's glide starts **sharp** (above the target) and falls to it
(G1: "≈ 3.5 % sharp… falls to about 1.5 % within 100 ms").

- [ ] **Step 1: Resolve the G1-vs-5-cent-bound tension explicitly, in
  writing, before implementing anything.** G1's own long-term figure —
  "then drifting toward 0.8 %" — is about 14 cents, past the 5-cent bound
  `TuningAccuracyTest`/`SilkTest`'s tuning tests enforce on every voice.
  Model only the sourced 100 ms fast transient (3.5 % → 1.5 %) continuing to
  a full settle at the plucked degree (0 %) by the point the tuning test
  measures (spec, "Testing", item 1: "SHAMISEN is measured after its
  built-in glide settles (from 150 ms)") — i.e., treat the 0.8 % asymptote
  as outside this phase's modelled range, not as a target to reach. Write
  this decision into the glide function's own KDoc, the same way
  `COURSE_FB_STEP`'s KDoc discloses an unresolved finding rather than
  silently picking a number - this is a **known, disclosed simplification**,
  not a silent contradiction of G1.
- [ ] **Step 2: Implement as a `Loop.retune` caller, built at the settled
  (lowest) frequency.** `retune`'s own contract requires the `Loop` be
  constructed at the glide's lowest frequency (the longest delay, since
  `maxN` is fixed at construction) and only ever retuned toward shorter
  loops afterward. SHAMISEN's glide runs high→low, so: build `tune`/`Loop`
  at the **settled** (target, lower) frequency exactly like `guzhengLoop`
  does for `plucked`; before the render loop's first sample, call
  `loop.retune(sharpStartFreq)` once (a higher frequency always needs a
  *shorter* loop than the one `maxN` was sized for, so this never trips the
  `t.n <= maxN` require); then glide `loop.retune(...)` back down toward the
  settled frequency over the sourced ~100 ms window, mirroring
  `oudCourseLoop`'s own per-sample progress loop. `sharpStartFreq = freq *
  2f.pow(Dsp.lin(pick, someFloor, 0.035f) / ln(2) / 1200 ...)` — work out the
  exact cents-to-ratio conversion the same way `oud`/`guzheng` already do
  (`freq * 2f.pow(cents / 1200f)`), with 3.5 % (≈ 59 cents) as PICK 1's own
  ceiling and some smaller floor at PICK 0 (a softer stroke stretches the
  string less — spec's own causal claim, no source gives PICK 0's exact
  floor, so pick a shape value and say so).
- [ ] **Step 3: Test the glide's own shape claim** (spec, "Testing": "the
  first 100 ms reads sharp and falls; the settled pitch is on the degree").
  Measure the instantaneous frequency (or `FineTuning`'s own `measuredHz`
  windowed early vs late) shows sharp-then-falling behaviour in the first
  ~100 ms, and lands within 5 cents of the target from 150 ms on — this is
  also, functionally, this voice's own version of the shared "in tune at
  every degree" test (item 1), so it can share plumbing with the
  OUD/GUZHENG/SANTUR tuning tests rather than being a fully separate case.
- [ ] **Step 4: Verify and commit.**

### Task 3: The body table and SLAP's skin layer

Two independent fixed-mode tables, both new to `Silk.kt`'s `bodyFor`-style
data (no `Strings.kt` change): the frame/neck bank BODY drives (reusing
`Strings.bodyRing` exactly as OUD/GUZHENG/SANTUR already do), and a small
skin bank SLAP drives (which needs new plumbing, since its own drive signal
is a synthetic burst, not the string's own first difference).

- [ ] **Step 1: The BODY table — four sourced modes, an inverted shape from
  OUD/GUZHENG's own tables.** Frame: 573.2 Hz (ζ = 0.605 %), 630.8 Hz
  (ζ = 0.854 %); neck: 67.55 Hz (ζ = 0.923 %), 85.38 Hz (ζ = 2.35 %)
  (research §1, B1–B4). `t60 = 2.2 * Q / f`, `Q = 1 / (2ζ)` — the same
  formula OUD's own body-mode KDoc already documents, giving roughly 1.76 s
  / 0.55 s / 0.32 s / 0.20 s respectively (matches the research note's own
  `computed` column). **Gains are the one place this table should read
  differently from OUD's and GUZHENG's:** those voices' lowest sourced mode
  is their *loudest* (nothing in their own research says otherwise), but
  SHAMISEN's radiated spectrum "peaks near 700 Hz and falls about 25 dB an
  octave below it" (R1) — the frame modes (573/630 Hz) sit close to that
  peak and should carry meaningfully more gain than the neck modes
  (67/85 Hz), which the same 25 dB/oct rolloff (roughly 3.4 octaves below
  700 Hz) would put around 85 dB down in the real instrument's own radiated
  balance. Shape the table's gain column to that qualitative fact rather
  than defaulting to OUD/GUZHENG's own low-mode-dominant pattern; say so in
  the KDoc, the same way GUZHENG's own body-mode gains are labelled shape.
- [ ] **Step 2: The skin table — one placeholder mode, explicitly
  unresolved.** B5 (≈ 151.7 Hz) and B6 (≈ 766.4 Hz) are the same lab's own
  two irreconcilable measurements of the mounted skin's fundamental
  (research §1, N.3 verifier note i) — do not pick one and call it settled.
  Ship one mode near the sourced *radiated* peak instead (700 Hz, R1/R2 —
  two independent labs, both anechoic-adjacent), labelled explicitly as a
  stand-in for the unresolved skin mode, the same "one neutral placeholder,
  not an empty table" precedent `Silk.bodyFor`'s own SANTUR entry set.
- [ ] **Step 3: `withSlap` — a new Silk.kt-private helper, not a
  `Strings.bodyRing` call.** `bodyRing`'s own contract treats its `string`
  argument as *both* the drive source (via its first difference) and the
  dry carrier the wet mix adds onto — SLAP needs a *different* drive (a
  short noise burst standing in for the bachi/skin contact, ~20 ms per A2's
  own touch-noise duration, or A3's own ~20 ms string–skin contact window)
  added onto the *unmodified* string, not derived from it. Build the burst
  the same way `Strings`'s own `rawBurst` does (filtered, zero-meaned
  noise), drive the skin table through `Modes.ring(burst, 1f, skinTable,
  rate)` directly (bypassing `bodyRing` entirely), pad to the skin table's
  own longest `t60` the way `bodyRing`'s own `pad` calculation does, and mix
  `out[i] = string[i] (0 past its end) + slap * wet[i]`. SLAP 0 returns
  `string` unmodified, matching every other character macro's own "0 is the
  plain string" contract.
- [ ] **Step 4: Test.** SLAP's own claim (spec, "Testing": "the first 20 ms
  gains broadband energy with SLAP; the tail does not") — compare a
  broadband-energy measure (RMS or spectral flatness) in the first 20 ms
  between SLAP 0 and SLAP 1, and confirm the tail (well past the skin
  table's own t60) is unaffected. SLAP 0 byte-identical to the plain string,
  the same assertion style `bodyRing`'s own `amount 0` test already uses.
- [ ] **Step 5: Verify and commit.**

### Task 4: The SHAMISEN voice

- [ ] **Step 1: Add `SHAMISEN` to `enum class SilkVoice`.** Forces every
  exhaustive `when (voice)` in `Silk.kt` to a compile error until a branch
  is added — confirm, the same way Phase 2's own Task 5 Step 1 did by
  reading the call sites directly, that `SilkPatch`/`Velocity.kt`'s generic
  dispatch still needs no edit for a fourth voice.
- [ ] **Step 2: `rootFor(SHAMISEN) = 130.81f` (C3)** — nagauta open string 1
  measures ≈ 131 Hz in honchōshi (research §1, P1; corroborated by P2's B2
  and P6's inferred ≈ 125 Hz), C3 the nearest named note.
- [ ] **Step 3: `macrosFor(SHAMISEN)`** — the shared seven plus SAWARI/SLAP
  (spec, "Macros" table): TUNE/SCALE (default MIYAKO_BUSHI — spec:
  "SHAMISEN → MIYAKO-BUSHI")/INFLECT/DAMP/PICK (bright default — "PICK
  high", mirroring GUZHENG's own 0.7)/STRIKE (default **1/6**, not the
  0.15 baseline other voices use — sourced: "the bachi meets the string at
  about 1/6 of its length… STRIKE's default is 1/6", A5)/BODY/SAWARI
  (character 1, default 0 — every character macro's own "0 is the plain
  string" convention)/SLAP (character 2, default shape — pick something
  small and nonzero so a factory pad carries a trace of the skin strike,
  the same reasoning SANTUR's own nonzero COURSE default used).
- [ ] **Step 4: `synthesize`'s SHAMISEN branch.** `Strings.pluck(freq,
  seconds, damping, pickHz, seed, rate, position, jawari = sawari,
  dispersion = shamisenDispersion, exciter = ::pluckExciter)` wrapped in
  Task 2's own glide envelope (a new private function analogous to
  `oudCourseLoop`/`guzhengLoop` but with the glide direction reversed and
  no macro gate — it always runs), then `withBody` (Task 3's frame/neck
  table), then `withSlap` (Task 3's skin layer) — BODY and SLAP are
  independent additive layers on the same underlying string, so this order
  (SLAP added after BODY, both onto the same carrier) is a implementation
  choice, not one the spec diagrams explicitly the way SANTUR's WASH-after-
  body ordering was; document the reasoning (SLAP's own skin-strike energy
  is a separate radiating path from the body frame's response to the
  string's bridge force, so it shouldn't be re-processed through the body
  resonators) in the branch's own comment.
- [ ] **Step 5: Verify against this voice's own tuning claim** — every
  degree of MIYAKO_BUSHI within 5 cents, measured from 150 ms on (Task 2's
  own glide-settle point), the same `measuredHz` machinery as every other
  SILK voice.
- [ ] **Step 6: Measure the classifier, don't assume the spec's own line.**
  The spec's "Testing" section says "all four defaults read TONAL" — Phase
  1b already found this line stale for OUD and GUZHENG (both classify PERC;
  a plucked string's own energy never crosses the classifier's
  bass-dominant gate) and corrected the roadmap rather than the code.
  Render SHAMISEN's own default and read its actual classification; write
  down whatever it measures, not what this line predicts.
- [ ] **Step 7: Commit.**

## What Phase 4 (presets) inherits

- All four SILK voices exist, registered, tuning-verified. Presets are
  authored by ear against a real render, the standing rule every phase's
  own roadmap row has repeated: presets authored blind are disposable.
- `Strings.Loop`'s `jawari`/`Collision` slot has now shipped on two voices
  (SITAR, SHAMISEN) at two very different scales (a buzz meant to be heard
  occasionally vs one central to the instrument's own identity) — useful
  precedent if a future voice needs a third.
- The G1-vs-5-cent-bound tension (Task 2) is a named, disclosed
  simplification, not a closed question — worth reading before authoring
  any SHAMISEN preset that leans on the glide's own character.
- PLUCK's own SITAR (spec: "PLUCK's SITAR can follow Phase 3 directly") is
  now unblocked on the toolkit side — `Collision`, `Dispersion` and the
  pitch envelope have all shipped and been exercised by a second and third
  voice — but remains PLUCK's own decision, in its own spec, per the
  Architecture section's own note ("PLUCK adopting dispersion or collision
  is PLUCK's decision, in its own spec").
