# Accord handoff review

Reviewed 31 October 2026. Read-only review of the main engineering spec, the three design audits, bundled Python sources and current materialized repository APIs. No new audio, Kotlin, repository or site changes. Line references below refer to the 416-line spec reviewed before subsequent edits; SHA-256 `6568bb5dcc881d4ab58d7270a0adacdb1ffe9220a7b8247de2c86f8ea9a0d7db`.

The handoff preserves the important owner decisions: BRUSH default, WOOD retained, original 5.96 TINE plus separate options, no fabricated audible benefit for 6.00, common eight-mode acoustic architecture, and finite playback distinct from a seamless loop. The remaining issues are specification ambiguities rather than evidence that the accepted sound direction is wrong.

## Must fix before freezing the handoff

1. **Bound the persisted source start.** Spec **65**, **170** and **299–301**: `sourceStartCycles` has a default but no allowed range, while the work/memory claims assume it never exceeds 8. The `.25..8` duration and 1..4 PACE bounds do not establish a 40-cycle maximum if the saved start is arbitrary. State the supported normal domain, for example finite 0..8 cycles or a 0/8 allowlist. Longer diagnostic starts need a separate bounded diagnostic interface. Validate this field at JSON precision and at the public boundary; include its limits in horizon tests.

2. **Make strict JSON macro validation explicit before Float conversion.** Spec **70**, **346**: the text explicitly demands raw-precision validation for note/velocity/seed but does not say that every raw macro value must itself be finite and within 0..1 before conversion. Current `Patches.decode` converts macro numbers to Float (`Patches.kt:155–158`); `Patches.validateMacros` then checks Float range (`:166–171`). A raw value `1.00000000001` can become `1f`. Require Accord's strict decoder to reject these values and unknown macro names before calling the common decoder. This does not conflict with the public direct-render `settled` policy; keep the tests separate, and say whether programmatic Patch construction follows strict saved-patch validation.

3. **Preserve the pressure interpolation order.** Spec **168**, **191–199**: “40 descriptor samples/cycle” and “linear pressure interpolation” could be implemented as nonlinear pressure evaluated at coarse knots and then interpolated. The approved renderer instead interpolates **theta and omega states from 40/cycle to a 2 kHz musical grid, evaluates the nonlinear pressure law there, then interpolates pressure to audio rate** (`reference/musicality/render.py:79–87`). Those operations do not commute. Spell out this compatibility path, including its 2 kHz grid origin and endpoint treatment. A denser path can be tested separately; it must not silently replace this readout while claiming approved BRUSH parity.

4. **Define the reference calibration recipe and measurement interval.** Spec **264–266**, **283**, **350–353**: a gain indexed only by voice/profile/note is appropriate, but the recipe used to obtain it is not fixed. State the reference seed/initializer, macro values, eight-second source and canonical start. State whether loudness is measured over the active eight seconds or the full source-plus-release buffer. The accepted TINE options were matched over active 0..8 seconds, while earlier voice/refinement comparisons used whole-file RMS (`acoustic-audit` calibration section; option renderer **83**, **123–137**). Whole-file measurement with different captured release lengths changes their relative active levels. Calibrate on one declared house-output reference and share the resulting static gain across velocity and control/seed/duration edits, rather than deriving a fresh gain from each edited performance. If headroom requires attenuation, apply one declared shared factor after the domain sweep. Distinguish house-loudness calibration from a claim of exact Python amplitude parity.

5. **Give initializer/seed behavior an implementable identity.** Spec **61–64**, **150–152**, **299**, **313**: the default initializer ID, its accepted values, and how the fixed NumPy fixture interacts with non-reference seeds are unspecified. A fixture initializer that always uses the saved arrays can legitimately ignore the seed only if the contract says so or restricts that combination; it must not pretend every saved seed chooses new phases. Define the default reference initializer, the separate project-RNG initializer, and any allowed seed/initializer combinations. For the project path, specify stable seed namespace/substream labels, a mechanical seed-version independent of acoustic revisions, phase mapping, centered/scaled rate algorithm and degenerate-vector policy. The mechanics audit already supplies a candidate centered/scaled rate algorithm and warns against reseeding mechanics on an acoustic model change. Current `Dsp.seedFor` returns a 32-bit Int and `Dsp.Noise.next()` returns Float (`Dsp.kt:147–175`); those facts do not provide a Gaussian generator or a Double uniform algorithm automatically. Pin the production roughness transform/statistical contract, or explicitly make selecting/freezing it an R0 native-listening gate. Preserve the exact reference arrays and their NPZ keys, which are present and readable.

6. **Normalize the numerical acceptance metrics.** Spec **172**: “relative energy residual <=1e-6” and “driven work residual <=1e-6” do not specify the denominator, whether this is maximum or endpoint error, the integration window, or the work quadrature accuracy. Define those quantities before calling them pass/fail gates. A useful conservative probe is maximum `abs(E(t)-E0)/max(abs(E0), floor)` over the declared window; the driven probe needs an explicitly scaled `E(t)-E0-integral(power)` residual and a tighter/independently checked power integral. “Bounded descriptor error” likewise needs a declared metric/threshold selected from the compatibility experiment. Keep the 256-step RK4, 2 microsecond timing and 150 ms latency numbers labeled proposed targets; the current DOP853 evidence does not validate them.

## Optional clarifications and implementation watchpoints

- **Short finite classification:** spec **66**, **321**, **346** correctly notes that default finite 8.9/10.2-second samples are classified LOOP by duration, without claiming seamlessness. At the minimum source, however, BASE/REFERENCE lasts only 1.15 seconds. Keep the actual-render classifier gate for these cases; if the real classifier chooses a drum category, restrict the supported short domain or revise the sound and audition it. Merely forcing `drumClassFor` to return TONAL would not satisfy the stated contract. Zero velocity must be tested against the actual silent classifier behavior separately.
- **Clear public boundary semantics:** spec **70**, **279**, **287** intentionally checks HOLD after settling, so a negative finite direct-render HOLD becomes zero while any positive settled HOLD is refused. The strict JSON path can reject all raw nonzero/out-of-range values. One sentence/example would avoid readers interpreting “reject nonzero HOLD” as a pre-settlement rule.
- **Silence during zero velocity:** exact all-zero output is easy to guarantee by an early return after parameter validation and frame-count calculation, with no mechanics rebuild. Preserve the requested duration/class contract for that silent result rather than inferring it from the nonsilent >1.5-second shortcut.
- **Solver candidate is honest:** fixed-grid extension, Double state, D positivity, work caps, causal ablations and measured-vs-proposed separation are strong. No must-fix objection to trying RK4 instead of implementing DOP853, provided parity gates choose its final grid and model identity.
- **Current source truth is materially correct:** the new FLOCK held representation, actual `KeyNote` path, current preparation caches, GYRE's incomplete integration and absence of `siblingPatches` are represented accurately. No need to revive the old 66-engine/export-gap claims.
- **Diagnostic archive prominence:** retaining `reference/refinement/render.py` with its explicit 6.00 override is appropriate provenance, but the README/entry points must continue to identify it as archived rather than a default production renderer. Main spec already makes that distinction clearly.
